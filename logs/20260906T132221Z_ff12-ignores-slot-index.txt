# 04f3:0c00 -- finger_info (ff 12) ignores its slot argument.
#
# FINDING
#   ff 12 returns the record of the MOST RECENTLY IDENTIFIED finger, not the
#   record for the slot named in payload byte 3. With no successful identify
#   since the device was opened, it returns a 2-byte `40 ff`.
#
# HOW IT WAS ESTABLISHED
#   Two `elanctl dump` runs, an hour apart, with a different last-identified
#   finger before each. All ten slots track the last match, not the index.
#   The second run was a stated prediction before it was made.
#
# WHY IT WAS MISSED FOR SO LONG
#   docs/MR330-report.md originally read the identical replies as "ff 12 is
#   rejected on every slot" and concluded the identify path could not complete
#   on 0c00. It completes fine. The identical-ness was the real signal; the
#   value was incidental. Cold-probing a match-on-chip command outside the
#   driver's state machine measured sensor state, not command support.
#
# IMPACT ON UPSTREAM elanmoc2: NONE TODAY.
#   Both finger_info call sites (IDENTIFY_GET_FINGER_INFO ~line 661, and the
#   enroll re-enroll check ~line 846) are preceded by an identify that names
#   the slot, so the driver always receives the record it expects. There is no
#   list/enumerate vfunc. The divergence is latent -- a landmine for any future
#   code that walks slots, not a live bug.
